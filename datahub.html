DataHub

Generic async data pipeline with SQLite persistence, Boost.Asio scheduling, and lock-free message queues.

Overview

DataHub is a header-only C++23 library providing a complete async data pipeline with zero runtime overhead via static polymorphism and compile-time reflection. It connects network sources (WebSocket, HTTP REST) to typed subscriber callbacks, with optional SQLite persistence at the data sink stage.

All scheduling runs on a shared Boost.Asio executor. A lock-free spsc_queue bridges the network receive thread to a dispatch strand, ensuring ordered, non-blocking delivery with no dynamic allocation in the hot path. Schema generation and JSON serialisation are handled at compile time via Glaze reflection — no registration macros, no runtime type maps.

Core components

▶
data_dispatcher<Acceptor...>

Receives raw JSON strings from any transport. Pushes each message into a lock-free spsc_queue (capacity 16) and posts a drain task onto a boost::asio::strand. The strand serialises processing — all adapter calls are ordered and thread-safe. Multiple adapters are tried via a C++23 fold expression (A₁ || A₂ || … Aₙ): the first adapter returning true consumes the message.

▶
data_adapter<DataType, Handler>

Deserialises a JSON string into a typed C++ struct using Glaze (glz::read_json). Calls the downstream handler and propagates its bool result — false means "not consumed", allowing fallthrough to the next adapter in the dispatcher chain.

▶
data_sink<Model>

Owns a shared_ptr<Model> (typically data_model). Calls model->accept(range) to persist incoming entities and receive back only the new or changed ones. Subclasses override handle_data(cache_type&&) and handle_error(exception_ptr). A generic_handler CRTP helper creates concrete subclasses from plain callables via the make_data_sink() factory. Data sinks without a data_model skip persistence entirely (e.g. order book).

▶
data_model<Entity, PrimaryKey>

SQLite DAO with RAII table creation on construction. Uses Glaze compile-time reflection to derive the table name, column types, and primary key — no hand-written SQL schema. accept() runs precompiled INSERT OR REPLACE statements and returns only the rows that were inserted or actually changed. Supports an optional table_suffix for per-symbol sharding. Full CRUD, count(), and drop_table() included. Implemented across metadata.hpp, query_builder.hpp, and operations.hpp.

▶
data_feed — two variants

In-memory cache sitting between the sink and subscribers. snapshot_data_feed clears and replaces the cache on every update, sending update_kind::snapshot to all subscribers. sorted_data_feed inserts new items in time-field order, deduplicates by a compile-time key field, and sends update_kind::increment — only the new items are delivered. Both variants give a new subscriber an immediate snapshot of the current cache on subscribe(). An optional filter predicate is evaluated before each insert.

▶
data_subscription<Entity, Container>

Abstract notification interface: handle_update(update_kind, Container const&). Subscribers are held as weak_ptr — expired subscribers are silently dropped on the next notification. A factory function make_data_subscription(callable) wraps any callable into a concrete subscription_handler.

Update semantics

snapshot_data_feed   update_kind::snapshot   — full replace; cache cleared before insert
      ↑
 HTTP REST              instruments, top-of-book

sorted_data_feed     update_kind::increment  — time-ordered; dedup by key field; new items only
      ↑
 WebSocket              public trades, private orders

A new subscriber always receives the current full cache as an initial snapshot regardless of which feed type they subscribe to. Subsequent notifications carry either the full replacement (snapshot) or the new-only incremental batch (increment).

Persistence — init and update cycle

When a data_feed is created it can be initialised from a data_model — all rows are loaded from SQLite into the in-memory cache so subscribers receive a complete state immediately on startup, even before the first network message arrives.

On every subsequent update, the data_sink calls data_model::accept() first — new or changed entities are persisted to SQLite — then passes only those new entities downstream to the data_feed. Unchanged entities (already in DB) are silently dropped.
